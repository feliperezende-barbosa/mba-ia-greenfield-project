  - A multipart of 2 parts needs a declared `sizeBytes` > 64 MiB (`64 MiB + 1` plans 2 parts); the declared size only plans the parts, the uploaded bytes (5 MiB + 1 MiB) are smaller, and `size_bytes` persists the real `HeadObject` length. MinIO accepts a single 0-byte part, so the `EMPTY_FILE` path is exercised end to end (integration + E2E).
  - The 10 GiB limit (`FILE_TOO_LARGE`, 413) is covered structurally in the unit test (`headObject` mocked at 10 GiB + 1 and exactly 10 GiB accepted), per `TD-09`.

The `ENQUEUE_FAILED` cause is logged with Nest `Logger` before the compensation (the domain exception carries only the catalog message); the detail is stored in `error_message`.
  - Parts are forwarded to `CompleteMultipartUpload` in the order the client sent them (an out-of-order list yields `InvalidPartOrder` → `422 UPLOAD_COMPLETION_FAILED`, as the Error Catalog states).

### SI-03.8 — MediaModule: metadados com ffprobe e thumbnail com ffmpeg
- **Status:** completed
- **Tests:** 34/34 passing (media.service.spec.ts 24, media.service.integration-spec.ts 10)
- **Observations:**
  - `execFile` is wrapped in a callback-based `run()` (not `util.promisify`) so unit tests can mock `node:child_process` and so `stderr` is available to classify errors. Classification: `Invalid data found when processing input` in stderr (ffprobe or ffmpeg) or no video stream / unparsable JSON / empty thumbnail output → `InvalidMediaError`; timeout (`killed`), HTTP errors (e.g. `404`), spawn failure and `maxBuffer` overflow → plain `Error` (retriable).
  - `probe` falls back to the video stream `duration` when `format.duration` is absent; `container` is the ffprobe `format_name` (e.g. `mov,mp4,m4a,3gp,3g2,mj2`); `-ss` is formatted with 3 decimals.
  - Timeouts are instance fields (`probeTimeoutMs`, `thumbnailTimeoutMs`, defaulting to the constants) so the integration spec shortens them to 500 ms and proves, with a local HTTP server that never answers, that a hung ffprobe/ffmpeg is SIGKILLed and the call rejects (validation note: a stalled process must not leave a video stuck).
  - `src/test/media-fixtures.ts` generates all fixtures with `ffmpeg -f lavfi` in an OS temp dir (removed in `afterAll`); the ≥ 11 MiB MP4 is a 5 s noisy `libx264 -crf 0` clip, and the helper throws if the result is smaller than 11 MiB.
  - No module-compilation test was added for `MediaModule` (single provider, no configured imports; DI wiring is exercised by the integration spec).

  - **Test isolation vs. the running worker:** the Compose `video-worker` consumes the default `bull` prefix; every suite that touches the queue (producer, videos service, worker, e2e) sets a unique `QUEUE_PREFIX` and obliterates its queue, so a live worker can never steal test jobs and tests never need it stopped. Suites that wipe DB tables (`cleanAllTables`) do not affect an idle worker.
  - Added `src/test/wait-for.ts` (polling helper) for the asynchronous worker assertions. `INVALID_MEDIA:` / `PROCESSING_FAILED:` prefixes live in `video-worker.constants.ts`. A missing video throws `UnrecoverableError` (the failed handler then finds no `processing` row and is a no-op).
  - `compose.yaml` `video-worker` uses the same `Dockerfile.dev` build, the `.:/home/node/app` volume, `depends_on` db/redis/minio `service_healthy` and `restart: unless-stopped`; `command` is `bash -c 'until [ -x node_modules/.bin/nest ]; …; exec npm run start:worker:dev'`. Scripts `start:worker` / `start:worker:dev` added to `package.json`.
  - Live verification: `docker compose up -d video-worker` → log `Video worker started, waiting for jobs`; a script (deleted afterwards) put a generated MP4 in MinIO, set the row to `processing` and enqueued through `VideoProcessingProducer` on the default `bull` prefix → the running worker moved the row to `ready` in ~150 ms (`duration_seconds` 3, metadata, `thumbnail_key` `videos/{publicId}/thumbnail.jpg`, thumbnail object of 37313 bytes in MinIO). `docker compose up -d --scale video-worker=2 video-worker` started two replicas (both logged the startup line); scaled back to 1.
  - Known caveat (not changed): `nest-cli.json` has `deleteOutDir: true` and both the API (`start:dev`) and the worker (`start:worker:dev`) compile into the same `dist/` through the shared mounted volume; concurrently starting two watch builds can briefly wipe each other's output. Not an issue for tests (ts-jest) or when only one of them is running; a separate `outDir` for the worker is a candidate follow-up.
